How it works

Claude Code는 어떻게 작동하나요?

VS Code 사이드바 또는 터미널에서 자연어로 질문하면, Claude가 아래 순서로 작동합니다.

1
VS Code에서 질문 입력 (사이드바 채팅 또는 터미널 claude)
2
CLAUDE.md 자동 읽기 — 프로젝트 규칙, 톤, 데이터 접근 방식 로드
3
Memory 참조 — 이전 대화에서 학습한 패턴/규칙 불러오기
4
Skill 키워드 감지 — "플랜 짜줘" → plan-builder 자동 실행
5
MCP + Plugin 호출 — Confluence 검색, Sheets 조회, 웹 리서치 병렬 실행
6
결과물 출력 — 리포트, HTML 페이지, Confluence 발행
📚
CLAUDE.md = 업무 매뉴얼
"한국어로 답변해" "Sheets URL은 read_sheet로" 같은 프로젝트 규칙을 정의. 대화 시작 시 자동 로드.
🔧
MCP = 업무 도구함
Confluence, Sheets, 웹 검색 등 외부 시스템 접근권. .mcp.json에 어떤 도구를 쓸지 정의.
📄
Skills = 업무 SOP
"의사결정 분석은 이 순서로 해" 같은 워크플로우. 키워드 감지 시 자동 실행.
🏭
Plugins = 앱스토어
Atlassian, GitHub, Slack 등 공식 연동. 한 줄 설치, OAuth 인증 자동.
🖥
VS Code 연동
사이드바에서 바로 채팅. 코드 선택 후 질문, 파일 탐색기 연동, 터미널 실행까지 하나의 화면에서.
File Structure

프로젝트 폴더 구조

~/Desktop/myproject/
CLAUDE.md
  └ 프로젝트 지시서 (자동 로드)

.mcp.json
  └ MCP 서버 설정 (어떤 도구를 쓸지)

.claude/
  ├ skills/
  │  ├ my-skill-1/SKILL.md
  │  └ my-skill-2/SKILL.md
  └ memory/
     └ MEMORY.md (대화 간 기억)

~/.claude/
  ├ mcp_server_configs.json (전역 MCP)
  └ plugins/ (마켓플레이스)
프로젝트 레벨 vs 유저 레벨
프로젝트 (.mcp.json): 이 폴더에서만 사용하는 MCP

유저 (~/.claude/): 어디서든 사용하는 MCP, 플러그인
플러그인
마켓플레이스에서 설치하는 공식 연동. /install-plugin atlassian 으로 설치. MCP와 비슷하지만 설정이 더 간편합니다.
Memory
대화가 끝나도 기억할 내용을 저장. "이 시트는 이렇게 파싱해" 같은 패턴을 학습합니다.
Plugins

Plugin vs MCP — 무엇이 다른가?

둘 다 Claude에게 외부 도구를 연결하지만, 설치 방식과 관리 범위가 다릅니다.

Plugin (마켓플레이스)
설치/install-plugin atlassian
인증OAuth 자동 (브라우저 팝업)
범위유저 레벨 (모든 프로젝트)
업데이트자동
설정 파일없음 (내부 관리)
MCP 서버 (수동 설정)
설치.mcp.json에 직접 작성
인증API 토큰 수동 입력
범위프로젝트 또는 유저 레벨
업데이트수동
설정 파일.mcp.json / mcp_server_configs.json
사용 가능한 주요 Plugin
Atlassian GitHub Slack Linear Notion Sentry Datadog
파란색 = PBrain에서 설치 권장  |  회색 = 필요 시 추가 가능
언제 뭘 쓰나?
공식 Plugin이 있으면 Plugin 사용 (설치 간편, 인증 자동). 커스텀 서버(PBrain MCP 등)나 공식 지원이 없는 도구는 MCP로 직접 설정.
Plugins FAQ

Plugin 자주 묻는 질문

Plugin과 MCP에 대해 가장 많이 궁금해하는 3가지.

Q. Plugin으로 설치하는 게 맞나요?
네, Plugin이 있으면 Plugin이 정답입니다.
설치 한 번이면 끝, OAuth 자동 인증, 자동 업데이트로 유지보수가 없습니다.
MCP가 필요한 경우는 두 가지뿐:
Plugin이 없는 서비스 (PBrain MCP, Redash 등) 더 세밀한 커스텀 제어가 필요할 때
Q. Plugin도 읽기/쓰기 다 되나요?
네, MCP와 동일한 수준으로 읽기·쓰기 모두 지원합니다.
GitHubPR 생성·머지, 코멘트, 파일 수정, 이슈 관리
AtlassianConfluence 페이지 읽기·생성·수정, Jira 이슈 생성·코멘트
Slack메시지 읽기·전송, 채널 관리
권한 범위는 OAuth 동의 시 설정한 scope에 따라 결정되며, 실행 전 사용자 승인 프롬프트가 동일하게 표시됩니다.
Q. 토큰 사용량 차이가 있나요?
차이 없습니다. Plugin이든 MCP든 Claude 입장에서는 동일한 "tool call"입니다.
토큰 사용량은 연결 방식이 아니라 요청·응답 데이터 크기에 따라 결정됩니다.
예시
Confluence 페이지 전체를 읽으면 Plugin이든 MCP든 같은 토큰을 소비합니다.

Skill 1

decision-dive — 의사결정 분석

사업 판단이 필요할 때, 내부 데이터 + 외부 리서치를 합쳐 구조화된 의사결정 리포트를 생성합니다.

~할까요? ~해야 할까? 검토해줘 비교해줘 A vs B 리스크
사용 예시
"구마모토 워킹투어를 정규 상품으로 출시해야 할까? 나오시마 대비 장단점 비교해줘"
결과물 구조
현황 요약 → 찬성 논거 → 반대 논거/리스크 → 옵션 비교 (2~3개) → 권장안 → 다음 액션
핵심 원칙
추측 금지, 데이터 없으면 "데이터 없음" 명시. 내부(Confluence) + 외부(Tavily) 교차 검증.
Skill 1 — 실제 결과물

decision-dive 출력 예시

decision-dive output
의사결정 딥다이브: 구마모토 워킹투어 정규 출시
분석일: 2026-02-28 | 내부 5건 | 외부 8건

현황
나오시마 투어 월 평균 32명 운영 중.
구마모토는 1회 파일럿 완료, 참가자 6명/8명 만석.

찬성 논거
1. 수요 검증 완료 — 파일럿 만족도 4.8/5.0
2. 원가 우위 — 가이드 위탁비 나오시마 대비 20% 저렴
3. 계절 보완 — 나오시마 비수기(겨울)에 구마모토 운영 가능

반대 논거 / 리스크
1. 교통 접근성 — 인천-구마모토 직항 주 3회뿐
2. 리소스 분산 — 1인 운영 체제에서 2개 목적지 병행 부담

옵션 비교
옵션내용리스크
A. 즉시 출시3월부터 정규 운영리소스 분산
B. 조건부 출시나오시마 비수기만 운영브랜딩 약화
C. 보류Q3까지 데이터 추가 수집시장 선점 실패

권장안
옵션 B 권장. 나오시마 비수기(12~2월)에 구마모토를 운영해 리소스 분산 없이 계절 보완 효과를 검증.
결과물 특징
• 찬반 논거에 수치 근거 필수
• 옵션은 항상 2~3개 (Go/Conditional/Hold)
• 권장안에 명확한 이유 1~2문장
• 출처(Confluence URL, Sheets명) 표기
데이터 흐름
Confluence → 파일럿 레슨런, 회의록
Sheets → 비용 시뮬레이션, 운영 데이터
Tavily → 구마모토 관광 트렌드, 직항 현황
Skill 2

plan-builder — 전략 플랜 수립

전략 방향, 로드맵, 실행 계획이 필요할 때. Mermaid gantt 타임라인까지 자동 생성합니다.

전략 플랜 로드맵 기획해줘 분기 계획
사용 예시
"2Q PB 사업 전략 플랜을 잡아줘. 나오시마 안정화 + 신규 목적지 탐색 방향으로"
결과물 구조
현황 & 문제 정의 → 목표 & KPI 테이블 → 전략 방향 (3~5개, Why/How) → 실행 계획 → Mermaid gantt → 리스크 대응
decision-dive와 차이
decision-dive는 "할까 말까"의 판단,
plan-builder는 "어떻게 할까"의 실행 계획.
Skill 2 — 실제 결과물

plan-builder 출력 예시

plan-builder output
2Q PB 사업 전략 플랜
기간: 2026.04~06 | 내부 7건 | 외부 12건

목표 & KPI
KPI현재목표측정
월 참가자 수32명50명Sheets 집계
투어 만족도4.74.8+설문
신규 목적지01개 파일럿출시 여부

전략 방향
전략 1: 나오시마 확장
Why: 월 32명 → 50명 성장 여력 존재
How: 주말 회차 추가, 마케팅 채널 다변화

전략 2: 신규 목적지 파일럿
Why: 계절 리스크 분산 필요
How: 다카마쓰 또는 구마모토 1회 파일럿

타임라인
gantt
  title 2Q 실행 타임라인
  section 나오시마 확장
    주말 회차 추가 :a1, 2026-04-01, 14d
    마케팅 테스트 :a2, after a1, 30d
  section 신규 목적지
    목적지 선정 :b1, 2026-04-07, 21d
    파일럿 실행 :b2, 2026-05-15, 14d
decision-dive와 차이
decision-dive: "할까 말까" → 옵션 비교 + 권장안

plan-builder: "어떻게 할까" → KPI + 전략 + 실행 + 타임라인
Mermaid gantt 자동 생성
타임라인이 Mermaid gantt 코드로 출력되며, Confluence 발행 시 SVG 이미지로 자동 변환됩니다.
핵심 원칙
• KPI는 반드시 측정 가능한 수치
• 전략은 3개 기본 (최대 5개)
• gantt 날짜는 오늘 기준 현실적 일정
• 담당자: "서기원" 또는 "PB팀"
Skill 3

biz-expansion-scout — 사업 기회 탐색

새로운 상품이나 목적지를 탐색할 때. 글로벌 벤치마크 + 한국인 수요 + 현지 환경을 4개 에이전트로 병렬 분석합니다.

어떤 상품 어떤 투어 사업 기회 벤치마킹 GYG 분석 시장 분석
사용 예시
"오사카에서 어떤 한국어 투어를 만들면 좋을까? GYG랑 에어비앤비 체험 벤치마킹해줘"
사업 기회 매트릭스
수요 (한국인 여행자 니즈) x 실현 가능성 (현지 파트너 환경) x PB 역량 (운영 가능 여부)의 3축으로 우선순위를 매깁니다. 목적지 언어로 현지 검색을 병행하는 것이 핵심.
Skill 4

partner-pitch-builder — 파트너 제안서

현지 오퍼레이터나 시설에 협업을 제안할 때. 수익 모델 시뮬레이션까지 포함된 제안서 초안을 생성합니다.

파트너 제안 제안서 수익 모델 수수료 어떻게 설득
사용 예시
"나오시마 베네세 측에 파트너십을 제안하고 싶어. 수익 모델이랑 제안서 초안 만들어줘"
결과물
파트너 유형별 가치 제안 → 수익 시뮬레이션 (판매가/변동비/고정비/배분율) → 제안서 초안 → Mermaid 수익 흐름도
특징
Sheets의 비용 시뮬레이션 데이터를 직접 참조해 실제 숫자 기반으로 작성. 파트너/PB 양쪽 관점 균형.
Skill 5

quarterly-growth-planner — 분기 OKR 설계

분기별 성장 목표와 성과 관리 사이클을 설계합니다. 목표 설정 + 측정 + 리뷰까지 한 번에.

OKR 분기 목표 Q2 플랜 성과 관리 올해 계획
사용 예시
"Q2 OKR을 설계해줘. 나오시마 안정화와 신규 목적지 파일럿 런칭이 핵심이야"
plan-builder와 차이
plan-builder는 전략 방향 + 실행 계획 중심이고, quarterly-growth-planner는 측정 가능한 OKR + 성과 관리 루프(월간 체크포인트, 분기 리뷰) 중심입니다. "무엇을 측정할지"에 집중합니다.
